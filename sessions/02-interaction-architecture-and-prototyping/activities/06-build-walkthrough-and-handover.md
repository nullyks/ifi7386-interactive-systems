# Activity 06 - Build, Walkthrough, and Handover

[← Session 2](../README.md) · [← Previous activity](05-prototype-fidelity-and-method-selection.md) · [Glossary](../../../resources/glossary.md) · [Academic readings](../../../resources/academic-readings.md)

**Time:** 26 minutes · **Format:** team build → paired-team walkthrough → handover

## Goal

Build a testable low-fidelity prototype that matches the architecture and interaction flow, then use one walkthrough to find a meaningful mismatch.

## Part 1 - Build

**Time: 14 minutes**

1. Represent every state needed by the main path and one selected alternative.
2. Build the user controls, information, and feedback required by the prototype question.
3. Mark simulated parts so the team knows what a person must operate.
4. Keep the architecture, state model, labels, and prototype consistent.
5. Do not add visual polish or features that do not help answer the question.

## Part 2 - Paired-team walkthrough

**Time: 8 minutes**

Each team receives one four-minute round.

1. Give the participant a short context and goal without explaining the interface.
2. Run the main path or selected alternative path.
3. The operator follows the agreed rules and does not improvise extra help.
4. The recorder notes actions, hesitation, questions, interpretation, and system-response mismatches.
5. The participant explains what state they think the system is in and what they would do next.

## Part 3 - Handover record

**Time: 4 minutes**

Record:

- prototype version and question;
- path that was walked through;
- one observed success;
- one observed mismatch between user expectation, prototype, flow, or architecture;
- one change to make before Session 3;
- one issue that needs evidence rather than an immediate design change.

## Feedback prompts

- What did you think would happen before you acted?
- What state did you think the system was in?
- Which feedback did you notice, and what did it mean?
- What would you do if the expected response did not occur?
- Which control, label, signal, or transition was hard to perceive or use?

## Output

Low-fidelity prototype version 1.1, a photo or screen capture, one walkthrough record, and one agreed change before Session 3.

## Between-session task

Finish a stable test version. Write one research question and two realistic user tasks. Keep the participant goal separate from instructions for using the interface. Bring the architecture, state model, accessibility review, prototype decision, operator script where relevant, and known limitations.
