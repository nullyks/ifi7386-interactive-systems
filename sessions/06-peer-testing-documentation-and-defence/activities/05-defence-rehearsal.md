# Activity 05 — Defence Rehearsal

[Session 6](../README.md) · [Previous activity](04-hardware-and-bom.md)

**Time:** 15 minutes · **Format:** two short rehearsals with feedback and a final gap check

## Goal

Practise the demonstration and design explanation, then assign the remaining gaps before the defence.

## Practise explaining the work

In your pair of teams, take about six minutes per team: **four minutes to demonstrate and explain, two minutes for questions and feedback**. Use the remaining three minutes to assign the gaps. This is a practice format; follow the instructor's announced format and criteria for the actual defence.

Build the explanation around the user and evidence:

1. **Problem and goal:** who is the user, in what context, and what are they trying to achieve?
2. **Working interaction:** demonstrate physical input → system state → understandable feedback. Identify what is implemented and what remains simulated.
3. **Two design decisions:** show before/after, evidence, an alternative, a trade-off and the result of checking the change.
4. **Credible handover:** point to the architecture, hardware/BOM, tested versions, one limitation and the next useful test.

Each member should be ready to explain a contribution and how it connects to the rest of the system. Divide speaking roles for this short rehearsal and rotate who answers questions.

Useful peer questions: **Why this input? What changed after testing? What happens when data stops? What did AI do, and how did you verify it? Could another person restart this version using your documentation?**

## Short defence checklist

- [ ] We can state the user, context, goal and evidence behind the problem.
- [ ] The main physical interaction works; we can show one failure/recovery path and identify simulation.
- [ ] Our architecture, code, hardware record and BOM describe the same system.
- [ ] We can justify two design changes with before/after evidence, alternatives and trade-offs.
- [ ] Test records identify versions, outcomes, help given, limitations and unverified claims.
- [ ] The repository has working startup instructions, evidence links and the server/firmware/hardware version record.
- [ ] We can explain our use of AI, the team's review and each member's contribution.
- [ ] We have assigned remaining gaps and checked the instructor's actual submission and defence requirements.

If the live demonstration fails, show a clearly dated recording or earlier test evidence if available, explain which version it shows and report the current failure. A backup is evidence of an earlier run, not proof that today's build works.

## Output

A rehearsal completed by each team, peer feedback, and an owner/next action for each important remaining gap.
